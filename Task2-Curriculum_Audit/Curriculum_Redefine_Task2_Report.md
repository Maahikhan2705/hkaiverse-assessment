# 1. Executive Summary

This report reviews the supplied B.Tech Artificial Intelligence and Data Science course map and proposes practical changes to strengthen readiness for AI, data science and software engineering roles by 2030. The objective is to retain the mathematical and computing foundations of the degree while making applied capability more visible through tested code, reproducible experiments, data-quality checks, deployment practice and integrated projects.

The supplied course map totals 166 credits across Semesters 1-8. This is the working baseline derived from the course information provided for this review; the exact batch-specific IFHE regulation and elective rules should be checked before the figure is treated as the definitive graduation requirement.

The proposal identifies 39 credits of courses for material assessment or practical-outcome redesign. Against the 166-credit working baseline, this is 23.5%, within the assignment’s 20-25% target. The proposal does not add graduation credits: changes are embedded in existing courses and the existing Special Project, subject to syllabus review and academic approval.

# 3. Audit Method and Criteria

Course titles indicate likely subject coverage, but they do not establish the precise lab content, teaching time or assessment depth. Recommendations therefore focus on outcomes to strengthen and evidence to collect rather than assuming that a skill is absent from current teaching.

| Decision | When to use it | Example |
| KEEP | A foundational subject remains important. | Retain Data Structures; assess complexity and tested implementations. |
| UPDATE | A valuable subject can use stronger practical outcomes. | Update Cloud Computing assessments with logs, configuration, health checks and rollback. |
| REVIEW | Possible overlap or low demand needs syllabus and outcome evidence first. | Review repeated introductory tooling only after mapping actual syllabi. |
| INTEGRATE | A capability is best demonstrated across subjects. | Connect data quality, AI evaluation, API delivery, security and documentation in SP301. |

| --- | --- | --- |

Preserve prerequisites: advanced AI depends on programming, mathematics, statistics, data structures and core ML.

Assess evidence rather than course labels: inspect syllabi, labs, rubrics and student work before making claims about coverage.

Teach durable principles alongside current tools to avoid dependence on a single vendor.

Make responsible practice assessable through privacy, security, bias, limitations and human oversight.

Measure whether changes help through common practical rubrics, reproducibility checks and internship/project feedback.

# 7. Proposed AI Systems Engineering Lab / Capstone

Working title: “Reliable AI Workflow Engineering Lab: From Prototype to Verified Service.” The preferred host is the existing 3-credit SP301 Special Project, with integration from Cloud Computing and Generative AI, subject to the official syllabus and faculty approval.

| Element | Design |
| Problem | A fictional office receives requests with category, description, priority and status. The goal is to help staff triage requests or draft responses without allowing AI to approve or send consequential actions independently. |
| Data | Synthetic records only: request ID, category, created date, priority, missing fields, suggested response and approval status. Do not use real student/applicant/staff data without formal permission and safeguards. |
| Workflow |  |
| Milestones | 1. Map process and assumptions. 2. Build deterministic baseline. 3. Add AI assistance and record prompts/model/date. 4. Run tests. 5. Add approval, logging and recovery. 6. Compare against baseline. 7. Hand over documentation. |
| Deliverables | Workflow map, synthetic dataset, repository, test log, prompt/model/date log, risk register, demo, setup guide and reflection. |
| Human control | AI may suggest or draft. A person approves external messages, official record changes and consequential decisions. |

## 7.1 Acceptance tests

A valid synthetic request produces the expected structured result.

Missing required fields are flagged for clarification instead of silently guessed.

Ambiguous or low-confidence AI output is sent for human review.

A duplicate request does not create duplicate downstream action.

An unauthorized user cannot perform a restricted action.

A simulated model/service failure returns a safe error and preserves the original record.

An audit log captures action, timestamp, status and approval outcome without exposing unnecessary sensitive data.

The final report compares measured outcomes with a baseline and states limitations.

## 8.1 Reflection

AI can accelerate drafting and offer candidate solutions, but the examples show why verification matters. The data-structure task required a precise definition of “first repeated”; the SQL example needed a clear denominator rule for NULLs and application status; and the GenAI example needed an explicit abstention rule. AI should be treated as an assistant, with tests and human review used to check its work.

If the assessment requires external-tool evidence or an independent human checker, preserve the exact prompts, actual model label, date, output and verification record. Do not guess hidden model/version details or claim checks that were not performed.
